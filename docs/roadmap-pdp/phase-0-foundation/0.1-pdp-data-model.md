# PRD: 0.1 — PDP Data Model

**Phase:** Phase 0 — Foundation
**Priority:** P0
**Depends on:** None — can start immediately
**Estimated scope:** Medium (no theme files; 8 metaobject definitions + 12 metafield definitions in the Shopify admin, plus 1 doc correction)

## Context

The homepage sprint established the metafield pattern in
`docs/roadmap-homepage/phase-0-foundation/0.5-metafield-definitions.md` and shipped the product
custom keys the product card reads today. Verified against the theme, six product-scoped `custom.*`
keys already exist: `product_badge`, `category_label`, `highlight_text`, `highlight_color`,
`card_image`, `radiator_image`. Only one metaobject definition is in use anywhere
(`metaobjects.subscribe_save`, consumed by `snippets/subscribe-save.liquid`). Every PDP section that
renders per-product content is blocked until the definitions below exist, because a Liquid lookup
against an undefined metafield returns `blank` and the section silently renders nothing.

## Goal

All eight metaobject definitions exist, and all twelve product metafields in TDD §3.2 resolve — nine
created here, `category_label` and `highlight_text` already live, and the twelfth being the TDD's
mis-named `badge`, which is satisfied by the existing `product_badge`. One product is fully populated
as the reference fixture that downstream PRDs build and verify against.

## Requirements

### Functional
- Create the eight metaobject definitions in TDD §3.1: `helps_with`, `offer`, `free_gift`,
  `product_description`, `how_to_use`, `how_to_use_step`, `ingredient`, `faq`.
- Create `how_to_use_step` **before** `how_to_use`, because `how_to_use.steps` is a
  `list.metaobject_reference` pointing at it and Shopify rejects a reference to an undefined type.
- Create the nine new product metafield definitions: `helps_with`, `offers`, `free_gift`,
  `product_description`, `how_to_use`, `pro_tip`, `ingredients`, `faqs`, `lab_report`.
- Populate one product end-to-end as the reference fixture: 4 helps-with entries, 2 offers, 1 free
  gift, 3 how-to-use steps, 4 ingredients, and the FAQ set from TDD §4.2.
- Correct TDD §3.2, which names the reused badge key as `custom.badge`. The key actually shipped and
  read by `snippets/product-card.liquid:54` is **`custom.product_badge`**. Do not create
  `custom.badge`.
- Correct TDD §3.2's claim that three metafields are reused from homepage. Six exist; the three
  unlisted ones (`highlight_color`, `card_image`, `radiator_image`) are also live on products.

### Non-Functional
- Every definition uses the `custom` namespace, per TDD §3.
- Metaobject definitions expose their entries to the Storefront API so Liquid can read them.

## Approach

No theme files change in this PRD. Work in the Shopify admin, or via the Admin GraphQL API using
`metaobjectDefinitionCreate` and `metafieldDefinitionCreate`. Order matters twice: `how_to_use_step`
precedes `how_to_use`, and all eight metaobject definitions precede the metafield definitions that
reference them. Field types come straight from TDD §3.1 — note that `product_description` carries no
description field of its own (body copy comes from the native `product.description`) and that
`pro_tip` is a plain `single_line_text_field` on the product rather than a field inside `how_to_use`,
so a merchant can edit the tip without opening a metaobject entry. `ingredients` and `faqs` are
`list.metaobject_reference` so rendered counts follow entry counts with no fixed row limit anywhere.
Record the fixture product's handle in `docs/roadmap-pdp/status-log.md` so every downstream PRD
verifies against the same data. Note that this project has two Shopify credential paths with
different scopes — the `.env` token and the MCP connection — and neither alone completes every admin
task.

## Expected Output

- 9 new product metafield definitions in the Shopify admin

- `docs/tdds/amrutanjan-pdp-sprint.md` §3.2 corrected: `custom.badge` → `custom.product_badge`, and

## Constraints

- A `metaobject_reference` field cannot be defined before its target metaobject definition exists.
- Definitions are store state, not theme code, so they do not travel with a theme push and are not
  captured by git. The status log is the only record.
- Do not write `config/settings_data.json` while `shopify theme dev` is running — it overwrites
  settings the local file lacks.
- `theme check` does not validate schema defaults or metafield existence; a clean lint run proves
  nothing here. Verify by reading a value back in Liquid on the fixture product.
