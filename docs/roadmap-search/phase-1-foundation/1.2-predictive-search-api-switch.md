# PRD: 1.2 — Predictive Search API Switch

**Phase:** Phase 1 — Foundation
**Priority:** P0
**Depends on:** 1.1 Search Settings & Code Retirement
**Estimated scope:** Small (1-3 files)

## Context

After 1.1 (`docs/roadmap-search/phase-1-foundation/1.1-search-settings-and-retirement.md`), the modal
snippet is pruned and the `"Search"` settings group is final. Typed results currently come from
`assets/predictive-search.js:45`, which fetches `/search?q=…&type=product,article,page&options[prefix]=last&section_id=search-modal-results`
— the standard search route with the `search` Liquid object, not predictive search. A fully-written
`sections/predictive-search.liquid` already exists in the theme using the `predictive_search` object
with `resources.products/articles/pages`, and **nothing references it**. Sprint §3.2 specifies
predictive search, so this PRD rewires to the section that is already there.

## Goal

Typed results served by the Predictive Search API through `sections/predictive-search.liquid`, with
collections requested as a fourth resource type, and a recorded answer to whether predictive-search
product objects expose the metafields `product-card` depends on.

## Requirements

### Functional
- **First task, before any rewiring:** smoke-test whether `predictive_search.resources.products` exposes `metafields.custom.*` by rendering one metafield in `sections/predictive-search.liquid` and hitting the endpoint directly. Record the result in `status-log.md` — it gates 4.1
- Change the fetch in `assets/predictive-search.js` to `/search/suggest?q={query}&resources[type]=product,collection,page,article&resources[limit]={{ search_results_count }}&resources[limit_scope]=each&section_id=predictive-search`
- Change the parsed element id from `#search-modal-section-results` to `#predictive-search-section-results`
- Change `data-section-id="search-modal-results"` to `"predictive-search"` on the input in `snippets/search-modal.liquid`
- Pass `search_results_count` from Liquid to JS via a `data-*` attribute — never an inline script
- Add `collections` to the resource handling in `sections/predictive-search.liquid` (`predictive_search.resources.collections`)
- Remove the hardcoded caps of 10 on articles and pages; the API limit governs. ⚠️ **Corrected during execution:** these caps were **not** in `sections/predictive-search.liquid`, which has no `limit` anywhere. They were `articles_shown < 10` / `pages_shown < 10` in `sections/search-modal-results.liquid:91,129` — the file this PRD **deletes**. Satisfied by the deletion; no edit existed
- Delete `sections/search-modal-results.liquid`, now orphaned
- Keep the existing 2-character minimum, 300 ms debounce and `AbortController` cancellation unchanged

### Non-Functional
- The request must still cancel in flight on a fast typist — the existing `AbortController` pattern is retained, not rewritten

## Approach

Use `/search/suggest`, **not** `/search/suggest.json` — only the former accepts `section_id` and
returns server-rendered section HTML, which is what keeps `product-card` renderable in Liquid.
`resources[limit_scope]` defaults to `all`, which would share one limit across all four types and
starve the product grid; set it explicitly to `each`. `resources[limit]` is bounded 1–10 by the
platform, which is why `search_results_count` is capped at 10 in 1.1. Styling stays untouched in this
PRD — `sections/predictive-search.liquid` keeps its current generic markup and is restyled in 4.1 and
4.2. This PRD is a wiring change only, so it can be verified by diffing the injected HTML rather than
by eye.

## Constraints

- The standard `/search` route accepts only `product`, `page`, `article` — collections are available **only** on the Predictive Search API, which is why Sprint §3.2's collections requirement forced this switch (D-11)
- Predictive search does not index metafields, so metafield values are not *searchable*; a query matching a `highlight_text` value will not hit. Rendering is a separate question — that is what the smoke test answers
- `resources[limit]` is hard-capped at 10 by the platform
- Switching away from the `/search` route gives up its semantic-search capability on eligible plans
