## Context

Sprint §4.12. The About Us band — full bleed, a background image with a `#466E280` green wash,
a centred heading and accent CTA, and a horizontal timeline of year markers (1893, 1993, 2003,
2026) with product counts and four highlight images.

The distinguishing feature is a **progress line that animates smoothly from the first block to
the last**, time-based, starting when the section enters the viewport via IntersectionObserver.
Per-step duration and loop behaviour are **OD3 — still open**.

Accent CTA measured: radius 20 / h50 desktop, radius 6 / h34 mobile (F1, as-designed).

## Goal

A full-bleed About Us band with a viewport-triggered animated progress line across
merchant-defined timeline blocks.

## Requirements

### Functional

> **This section paints a background, so it takes BOTH:** `margin` on the wrapper for its separation from neighbours, and `padding` on the element carrying the background for the painted interior. Margin falls outside the painted box, so without the padding the band collapses to the content height (CLAUDE.md §5).
- Section-level: heading (`richtext`, underline-enabled), button label (`text`), button link (`url`)
- Block type `milestone` with: image (`image_picker`), timeline (`text`, the year label), label (`text`, the product count)
- Progress line animates from first block to last, **time-based**, triggered by IntersectionObserver on section entry
- Full bleed — no side padding at any breakpoint
- Button arrow embedded in code from 1.1
- The final milestone marker is visually distinct (the extraction shows a `#EAB308` 3px ring on the 2026 ellipse)
- `presets` with four milestone blocks; no `max_blocks`

### Non-Functional
- **`prefers-reduced-motion: reduce` renders the line in its completed state with no animation**
- Animation runs once per page view unless OD3 specifies looping
- Background image as `<picture>`, lazy, with the green wash as a CSS overlay layer

## Approach

**OD3 must be resolved before this ships.** Per-step duration and loop behaviour are unspecified.
Do not invent values silently — propose defaults in the PR (a defensible starting point is
~800ms per step, no loop, animate once) and get them confirmed, or expose them as section
settings so the merchant decides. Exposing them as a `range` for step duration and a `checkbox`
for loop is the lower-risk path and turns an open decision into a merchant control.

Animate with CSS `transform: scaleX()` or a `width` transition on a line element driven by a
class toggled from an IntersectionObserver, not with `requestAnimationFrame` — a CSS transition
is cheaper and honours `prefers-reduced-motion` naturally via a media query override.

Wrap the behaviour in a Web Component with the `customElements.get()` guard, per Global
Standards §6.4. Disconnect the observer after firing so it does not re-trigger on scroll.

The desktop layout places milestones across a wide row with connecting lines and the highlight
images below; mobile stacks to a narrower arrangement — the extraction shows a `Quote Section`
switching from `layout=row gap=400px` on desktop to `layout=column gap=143px` on mobile. Read
the element trees rather than inferring.
