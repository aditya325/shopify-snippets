# PRD: 5.2 — Performance Pass

**Phase:** Phase 5 — Assembly & QA
**Priority:** P0
**Depends on:** 5.1 homepage-assembly
**Estimated scope:** Medium (4-7 files)

## Context

Global Standards §7 sets the performance rules — picture elements with correct srcset, lazy +
`decoding="async"` below the fold, no CSS background images, first hero slide eager with
`fetchpriority="high"` and preloaded, `font_picker`-sourced fonts with above-the-fold weights
preloaded (Space Grotesk 700, DM Sans 400/600 — hand-written `<link>` tags carrying `crossorigin`,
since `preload_tag` cannot take a `font_url`),
per-section scripts loaded only where the section is present, and third-party app scripts
deferred and main-thread-audited.

It names **Lighthouse mobile as the per-section performance gate but states no threshold.**
Establishing that threshold is part of this PRD — a gate with no number cannot pass or fail
anything.

Each section PRD carried its own performance criteria. This PRD verifies them **in aggregate**,
on the assembled page, where the real problems live: sixteen sections competing for one main
thread, five Embla instances, two third-party widgets and a long image payload.

## Goal

The assembled homepage meets an agreed Lighthouse mobile threshold, with LCP, image loading,
font loading and script loading all verified against Global Standards §7 on the real page.

## Requirements

### Functional
- **Agree and record a Lighthouse mobile threshold** before measuring — Performance score plus explicit LCP, CLS and TBT targets
- Verify exactly one image is eager with `fetchpriority="high"` — the first hero slide — and that it is the measured LCP element
- Verify every below-fold image is `loading="lazy"` + `decoding="async"`
- Verify no CSS background images are used for content anywhere on the page
- Verify only above-the-fold font weights are preloaded, and that no preloaded font goes unused
- Verify per-section JS loads only where its section is present — nothing carousel-related on a page with no carousel
- **Audit third-party main-thread cost** for Judge.me and Quinn (or record as deferred if D2/D3 are unlanded)
- Verify all five Embla instances initialise exactly once and do not contend on scroll

### Non-Functional
- Measurements taken on a throttled mobile profile, not desktop
- Results recorded so later pages can be compared against the same baseline

## Approach

Set the threshold first, in writing, with the team. Without it this PRD has no pass condition.
A defensible starting point for a media-heavy D2C homepage on Shopify is Performance ≥ 70 mobile
with LCP < 2.5s and CLS < 0.1, but that is a proposal to confirm, not a given.

Then measure before optimising. Run Lighthouse mobile on the assembled page and capture the
baseline, so every subsequent change can be attributed. Optimising blind is how the hero preload
ends up loading five images.

The highest-risk items on this specific page, in order: the hero preload (easy to over-preload
across slides or viewports), the total image payload across sixteen sections, the two
third-party widget scripts, and five Embla instances all binding scroll listeners.

For fonts, check for the common failure — preloading a weight that `font_modify` returned `nil`
for in 0.4, producing a preload for a font that never loads. Cross-check the preload list
against the verified weight list.

If D2/D3 have not landed, the third-party audit cannot be completed. Record that explicitly as a
deferred item with a named owner rather than passing the PRD as if it were done.

## Expected Output

- Recorded Lighthouse mobile threshold, agreed and written down
- Baseline and post-optimisation Lighthouse reports for the assembled homepage
- Fixes across section files, `layout/theme.liquid` and `snippets/image-preloads.liquid` as measurement dictates
- A written record of any deferred third-party audit with owner

## Dependencies
