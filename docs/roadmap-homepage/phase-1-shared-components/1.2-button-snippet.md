# PRD: 1.2 — Button Snippet

**Phase:** Phase 1 — Shared Components
**Priority:** P0
**Depends on:** 0.2 colour-tokens, 0.4 typography, 1.1 icon-set
**Estimated scope:** Small (2-3 files)
**Amended:** 2026-08-11 — extended from a colour-and-stroke wrapper into a full button component. See "Extension" below.

## Extension (2026-08-11)

The first delivery (2026-08-10) shipped a good *colour-and-stroke* component and an incomplete
*button*: it hard-coded `type="button"`, and had no disabled state, no loading state, no icon
beyond a trailing arrow, no icon-only rendering, no rich label, and no way to pass `aria-label`,
`id`, `name` or `title` except through the raw unescaped `data_attributes` string. A repo audit
found **40 hand-rolled `<button>` elements** (14 submits, 11 icon-only, 18 with `aria-label`,
~25 distinct `data-*` hooks) plus ~20 anchors styled as CTAs, against exactly **one** live
`{% render 'button' %}` call site — so `DEFINITION-OF-DONE.md:73` ("one shared `button.liquid`
renders every button on the page") was unreachable.

This amendment adds, without changing any rest or hover value already delivered:

- **A named `size` scale** — `xs`, `sm`, `md`, `lg`, `xl`, `2xl`, `pill`, `badge`, one per measured
  placement, as `.button--size-*` in `assets/base.css`. **This reverses the D-5 decision recorded
  on 2026-08-10** ("no `size` param ships"), and restores this PRD's own Approach line 74. D-5's
  reason — "seven placements share no dimensional values" — held for the values but missed that
  every one of those shapes has a *named future consumer*, which makes it a design-system size
  rather than a one-off. `class_name` still overrides, per property and per breakpoint.
- **Element and state control** — `type` (allowlisted `button`/`submit`/`reset`), `disabled`,
  `loading`, `with_loader`, plus `.button[disabled]`, `.button[aria-disabled='true']` and
  `.button.is-loading` in `base.css`, and a zero-specificity `:not(:where(...))` guard so the
  hover swap cannot fire on a disabled or loading button.
- **Icons** — `icon` (dispatched by `case` over the 1.1 set), `icon_position`, `icon_class`,
  `icon_size`. `with_arrow` becomes shorthand for `icon: 'arrow-right'`.
- **Rich content** — a `content` parameter taking pre-captured HTML, for labels the escaped
  `label` cannot express (a price, two-tone text). `content` wins over `label` and is *not*
  promoted to `aria-label`, because that breaks WCAG 2.5.3 Label-in-Name when the rich content
  carries extra text.
- **Accessibility and form attributes** — `aria_label`, `aria_controls`, `aria_expanded`,
  `aria_pressed`, `aria_describedby`, `aria_haspopup`, `id`, `name`, `title`, `target`, `rel`.
  `aria_expanded` / `aria_pressed` are **strings**, because Liquid's `default` filter treats a
  passed `false` as unset.
- **`variant: 'unstyled'`** — emits `.button` alone, so a legacy surface can adopt the behaviour
  without inheriting design-system colour. This is what makes the deferred migrations visually inert.
- **The blank guard is relaxed** — the snippet renders nothing only when `label`, `content` **and**
  `icon` are all blank, so icon-only buttons become expressible.
- **Criterion 6 (focus-visible) is now MET** — see the amended non-functional list below.

**Deliberately excluded:** `form`, `value`, `formaction`, `role`, `tabindex`, `onclick` — the audit
found zero call sites. `data_attributes` stays the escape hatch for genuinely one-off needs, and is
emitted last so it can add attributes but never override a generated one.

**Migration is explicitly out of scope.** No call site is converted by this amendment; the ~37
remaining hand-rolled buttons migrate with the PRDs that own their surfaces. The newsletter's
existing call site renders byte-identically.

## Context

There is no button snippet in the theme. `snippets/add-to-cart-button.liquid` exists but is
specific to the cart flow. Global Standards §6.1 calls for one snippet with variants, and
Sprint §2.5 has already measured every variant's fill, text colour, type and radius.

**F1 is resolved here as as-designed per placement.** F1 asked whether to unify radii or keep
them per placement; since every value is measured, this PRD builds them as designed. Radii
therefore vary by placement and that is intentional, not a bug.

**F3 is resolved** (2026-08-07) — the hover pattern is an inverse fill/text swap, specified in
full below. Hover now ships. Global Standards §6.1 and Sprint §5 still say otherwise and are
corrected as part of this PRD.

## Goal

One `snippets/button.liquid` rendering all five measured variants with correct fill, stroke,
type, radius and height at both breakpoints, with the CTA arrow embedded where the design shows
one.

## Requirements

### Functional
- Five variants per Sprint §2.5: `primary` (#466E2E fill, white text, DM Sans SemiBold 16 D / 14 M), `secondary` (transparent, 1px #466E2E stroke, green text), `pill` (white fill, per-block coloured text, radius 20), `accent` (#F4C430 fill, dark text), `badge` (#F4C430 fill, 0.5px #2A7A50 stroke, DM Sans Medium 12, green text, radius 8)
- Radius as measured per placement: hero primary 12 D / 6 M; card Add to Cart 10 at h44, 6 at h36–40; View All 20 D / 12 M; accent CTA 20 D / 6 M; pill 20
- Accepts `label`, `link`, `variant`, `with_arrow`, plus optional `bg_color` / `text_color` overrides for the blocks whose schema exposes them
- Renders `<a>` when `link` is present, `<button>` when not
- Arrow icon comes from 1.1 and is embedded in code, never a merchant field
- Renders nothing when `label` is blank

### Hover states (F3, resolved)

Transition **150ms ease**, on `background-color` and `color` for the button variants and on
`opacity` for the banner pill. Nothing else animates. A **1px stroke is present in every state**
on primary, secondary and accent — never added or removed on hover — so the button cannot
reflow. On primary and accent at rest the stroke colour equals the fill colour, making it
invisible until the fill goes transparent.

| Variant | Default | Hover |
|---|---|---|
| Primary | fill `#466E2E`, white text, 1px `#466E2E` stroke | transparent fill, `#466E2E` text, 1px `#466E2E` stroke |
| Secondary | transparent fill, `#466E2E` text, 1px `#466E2E` stroke | fill `#466E2E`, white text, 1px `#466E2E` stroke |
| Accent | fill `#F4C430`, dark text, 1px `#F4C430` stroke | transparent fill, `#F4C430` text, 1px `#F4C430` stroke |
| Banner pill | white fill, banner-coloured text | no colour change; `opacity: 0.9` on **block** hover (the pill is a non-interactive span — see 2.7) |
| Product badge | `#F4C430` fill, green text | none — not interactive |

Cards get **no** hover state, in any section.

### Non-Functional
- Focus-visible state present and meeting contrast — focus is accessibility, separate from hover.
  **Met by the 2026-08-11 amendment**: `.button:focus-visible` paints a 2px `--color-foreground`
  outline at `outline-offset: 2px` over a 4px `--color-primary-foreground` halo. `outline` is
  outside the border box, so nothing reflows
- Minimum 44×44 touch target on mobile where the design allows — **still not met**, and still
  deferred. Closing it needs either changed measured heights or an overlay that intercepts clicks
  on adjacent elements, which is a per-placement design decision
- Hover rules must not fire on touch devices as sticky states

## Approach

Single snippet with a `variant` parameter mapping to a Tailwind class string, following the
`{% doc %}` + `{%- liquid -%}` defaults pattern already used in `snippets/product-card.liquid`.
Keep the class strings literal in the Liquid so Tailwind's scanner can see them — do not build
class names by string concatenation, or they will be tree-shaken out of `assets/tailwind.css`.

Radius and height vary by placement rather than by variant alone, so expose `size` (or explicit
`radius` / `height`) as a parameter rather than hardcoding one radius per variant. Sprint §2.5
is the source of truth for every value; take the exact numbers from
`.buildspace/artifacts/home-page/design-context.md` where §2.5 is ambiguous.

Implement hover in `assets/base.css` rather than as Tailwind `hover:` utilities — the always-on
stroke plus the paired fill/text swap is three coupled declarations per variant, and a BEM-ish
rule keeps them together and auditable. Wrap the rules in `@media (hover: hover)` so touch
devices do not get sticky hover states after a tap.

This PRD also owns the documentation corrections the F3 resolution requires: Global Standards
§6.1 currently says "no hover ships until answered", and Sprint §5's F3 row is still open. Both
must be updated in the same PR, or the next person to read them will disable working hover.

## Constraints

- The 1px stroke is present in **every** state on primary/secondary/accent — adding it on hover would reflow the button
- Cards get no hover state; the product badge is not interactive
- Tailwind class strings must be literal for the scanner; no dynamic class construction
- Arrows embedded in code, never merchant fields
- Radii are as-designed per placement — do not normalise them
