# PRD: 1.4 — Newsletter Snippet Extraction

**Phase:** Phase 1 — Shared Components
**Priority:** P0
**Depends on:** 0.2 colour-tokens, 0.4 typography, 1.2 button-snippet
**Estimated scope:** Small (3 files)

## Context

Sprint §4.7 (subscribe-letter) and §4.17 (footer) both state that the email capture "reuses
themex newsletter.liquid". But `newsletter.liquid` is a **section** (94 lines,
`sections/newsletter.liquid`, paired with `assets/newsletter.js`), and Shopify does not permit
rendering a section inside another section. Taken literally, the sprint instruction cannot be
implemented.

The section's form markup is straightforward — a `<div data-newsletter-form
data-action="/contact">` with a hidden `form_type` input — and `assets/newsletter.js` binds to
it by data attribute, so the behaviour is already decoupled from the section shell.

## Goal

The newsletter form exists as `snippets/newsletter-form.liquid`, renderable from any section,
with `sections/newsletter.liquid` refactored to render it so there is exactly one copy of the
form markup and behaviour.

## Requirements

### Functional
- New `snippets/newsletter-form.liquid` containing the form markup, input, button and success/error states
- `sections/newsletter.liquid` refactored to `{% render %}` the snippet — its schema, settings and current rendered output are unchanged
- Snippet accepts parameters for the pieces that differ between placements: placeholder text, button label, layout direction, and a style variant (the subscribe-letter and footer treatments differ visually)
- `assets/newsletter.js` continues to bind by `data-newsletter-form` with no changes to its contract
- Multiple instances on one page each work independently — the homepage renders it twice (subscribe-letter and footer)

### Non-Functional
- Input has an associated label (visually hidden is acceptable), correct `type="email"`, and `autocomplete="email"`
- Success and error messages are announced to assistive technology

## Approach

This is a refactor, not a rewrite. Move the existing markup out of
`sections/newsletter.liquid` into the new snippet verbatim first, verify the standalone section
still renders and submits identically, and only then parameterise. That ordering keeps the
regression surface small and makes any breakage obvious.

Check `assets/newsletter.js` for anything that assumes a single instance per page — a
`document.querySelector` rather than `querySelectorAll`, or module-level state. The homepage
renders two instances, so if the script only binds the first, fix it here following the
`customElements.get()` guard pattern used elsewhere in the theme.

Keep the `data-action="/contact"` contract intact; Shopify's customer form posts there and the
existing script depends on it.

The button comes from 1.2 rather than being hand-written, so the subscribe-letter and footer
buttons match the rest of the system.

## Expected Output

- `snippets/newsletter-form.liquid` — parameterised form with `{% doc %}`
- `sections/newsletter.liquid` — refactored to render the snippet, behaviour unchanged
- `assets/newsletter.js` — multi-instance safe if it was not already

## Dependencies

### Upstream (must be done first)
- 0.2 colour-tokens, 0.4 typography
- 1.2 button-snippet — the submit button

### Downstream (unblocked by this phase)
- 2.9 subscribe-letter
- 4.2 footer

## Constraints

- A Shopify section cannot be rendered inside another section — this is the whole reason the PRD exists
- `sections/newsletter.liquid` must keep working; it may be in use on other templates
- Use `{% render %}`, never `{% include %}`
- DOM targeting stays on `data-*` attributes

## Acceptance Criteria

- [ ] `snippets/newsletter-form.liquid` exists and is renderable from a section
- [ ] `sections/newsletter.liquid` renders the snippet and its output is byte-comparable to before the refactor
- [ ] Two instances on one page both submit successfully and independently
- [ ] Submitting a valid email succeeds; an invalid one shows an error without a page reload
- [ ] Placeholder, button label, layout and style variant are all parameterised
- [ ] Input has a label, `type="email"` and `autocomplete="email"`
- [ ] Success and error states are announced to screen readers
- [ ] `assets/newsletter.js` binds every instance, not just the first
