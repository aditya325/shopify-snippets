# PRD: 0.1 — Breakpoint Alignment

**Phase:** Phase 0 — Foundation & Unblock
**Priority:** P0
**Depends on:** None — can start immediately
**Estimated scope:** Small (1-3 files, plus regression sweep)

## Context

`tailwind.config.js` currently declares `xs: 480px, sm: 640px, md: 768px, lg: 1024px,
xl: 1280px, 2xl: 1536px` — these are Tailwind-ish defaults carried over from the themex
boilerplate. Global Standards §2 specifies `xs 375, sm 430, md 768, lg 1024, xl 1280,
2xl 1536`. The `md` and above values already match; only `xs` and `sm` differ. The approved
decision is that the TDD wins. Every responsive utility written from Phase 1 onward inherits
these names, so this must land before any component work.

## Goal

`tailwind.config.js` breakpoints match Global Standards §2, with the 29 existing themex
sections verified to still render correctly at the new `xs` and `sm` values.

## Requirements

### Functional
- `tailwind.config.js` `theme.screens` reads `xs: '375px'`, `sm: '430px'`, `md: '768px'`, `lg: '1024px'`, `xl: '1280px'`, `2xl: '1536px'`
- Tailwind rebuild produces `assets/tailwind.css` with the new media query boundaries
- All existing `xs:` and `sm:` prefixed utilities across `sections/`, `snippets/`, `layout/` are inventoried before the change and re-checked after

### Non-Functional
- No visual regression on the existing themex pages: collection, search, cart, product, blog, article, customer account

## Approach

Grep the theme for `xs:` and `sm:` utility prefixes first — these are the only classes whose
behaviour changes. The design frames are 390px (mobile) and 1440px (desktop); the old `sm: 640`
sat above 430, so any utility that previously activated at 640 now activates at 430 and will
apply on large phones where it previously did not. Build the inventory, change the config, run
`npm run build`, then walk each affected template at 375 / 390 / 430 / 480 / 640 widths.

Where an existing themex section genuinely needs the old boundary, do not reintroduce the old
value — retarget that specific utility to `md:` instead, so the breakpoint vocabulary stays
canonical. Record any such retarget in the PR description.

## Expected Output

- `tailwind.config.js` — updated `theme.screens`
- `assets/tailwind.css` — regenerated
- A short inventory note (in the PR, not a committed file) listing every `xs:`/`sm:` utility found and its verification status

## Dependencies

### Upstream (must be done first)
- None

### Downstream (unblocked by this phase)
- 0.3 spacing-tokens — section padding utilities are breakpoint-scoped
- All of Phase 1 and Phase 2 — every component is authored mobile-first against these names

## Constraints

- `assets/tailwind.css` is generated; never hand-edit it
- Custom CSS may not go in `src/input.css` (Tailwind directives only); component styles belong in `assets/base.css`
- The mobile design frame is 390px, which now sits between `xs` (375) and `sm` (430) — base-layer styles must be correct at 390 with no prefix

## Acceptance Criteria

- [ ] `theme.screens` in `tailwind.config.js` exactly matches Global Standards §2
- [ ] `npm run build` completes and `assets/tailwind.css` contains `@media (min-width: 375px)` and `@media (min-width: 430px)`
- [ ] Every pre-existing `xs:`/`sm:` utility in the theme has been located and visually verified
- [ ] Collection, search, cart, product, blog and customer-account templates render correctly at 375, 390, 430, 640 and 768px
- [ ] No `xs`/`sm` values remain that contradict the TDD, and any retargeted utility uses `md:` rather than a reintroduced custom value
