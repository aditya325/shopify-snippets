# PRD: 4.1 — Editor Wiring and Default Content

**Phase:** Phase 4 — Assembly & QA
**Priority:** P0
**Depends on:** all of Phase 3 (3.1, 3.2, 3.3, 3.4)
**Estimated scope:** Medium (1 section preset + admin configuration)

## Design Reference

- **File:** https://www.figma.com/design/MpunnzguzvJ2SsXESNVVZ7/Development-For-INTENT?node-id=389-22801
- **Frames:** all 17 — this PRD populates the header so every frame has a live counterpart
- **Extraction:** `.buildspace/artifacts/navigation/` — already complete

## Context

Every panel now renders, but the header ships empty — a merchant installing the theme sees a bar
with no panel content. This PRD populates the 23 `rail_item` blocks and 2 `content_card` blocks so
the built header matches the design, and makes that state reproducible rather than hand-configured.

This is also the first point where the whole schema is exercised at once, so it is where the
50-block ceiling is **verified against a real build** rather than an estimate.

> ⛔ **The TDD is frozen.** Never edit `docs/tdds/amrutanjan-navigation-sprint.md`. Counts and
> decisions go to `status-log.md`; departures go to `deviations.md`.

## Goal

The header renders the full designed menu out of the box, with a block count comfortably under the
platform limit and a preset that reproduces it.

## Requirements

### Functional
- 23 `rail_item` blocks configured: 7 Shop By Need, 6 Categories, 6 Combo, 2 About, 2 Media
- 2 `content_card` blocks under the About → Our Story rail item
- Every rail item wired to its collection, blog or icon as applicable
- `show_subscribe_promo` on for Combo, About and Media; off for Shop By Need and Categories
- Utility strip labels and links set: Store Locator, Free Expert Consultation
- Section preset in `{% schema %}` reproducing this configuration on a fresh install
- Block ordering verified: every `content_card` follows its `rail_item`

### Non-Functional
- Total block count recorded and ≤30, leaving ≥20 blocks of headroom under Shopify's 50 cap

## Approach

Configure through the theme editor first, then lift the resulting `header-group.json` into a
`presets` entry so the state is reproducible. A preset is what makes this survivable — a
hand-configured header is lost the moment someone reinstalls the theme.

Verify the ordering rule **empirically**, not by inspection: drag a `content_card` above its
`rail_item` in the editor, confirm the warning appears and the card stops rendering, then drag it
back. That is the criterion 2.2 wrote and this is where it is exercised.

Watch the label decisions recorded in 0.1 and noted in 3.2 — Combo vs Bundles, Media vs Blogs, and
the Categories rail. Configure to the recorded decision; do not silently reintroduce the mobile
strings.

Take a block count at the end and record it. If it exceeds 30, something in the 2.2 model regressed
to a per-item block and needs finding before 4.3.

## Expected Output

- `sections/header.liquid` — `presets` entry reproducing the full configuration
- `sections/header-group.json` — populated header state
- Block count and label decisions recorded in `docs/roadmap-navigation/status-log.md`
